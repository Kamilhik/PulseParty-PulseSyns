# Архитектура и исследование API

## Основной вариант 0.3.0: обычный PulseSync

По последнему уточнению пользователя хост не изменяется. Основная сборка использует только SDK `net.fetch` и общий HTTPS-сервис: Cloudflare Worker маршрутизирует запросы в один `PulsePartyRooms` Durable Object. Он переиспользует `Rooms`, проверяет роли, epoch/sequence, сессии и opId и держит авторитетное состояние в памяти. Один объект исключает независимые копии комнат в разных Worker isolates. При вытеснении/перезапуске комнаты завершаются. Миграция класса SQLite-backed совместима с Free, постоянная БД комнат не используется.

В стандартной сборке `companionUrl` пуст, циклы native bridge и сопряжение отключены. Нет чтения обязательного bridgeToken, регистрации протокола ОС, native iroh и Discord IPC. `PULSEPARTY_RELAY_URL` задаётся при сборке одновременно с разрешённым `/v1` в манифесте. Без адреса нет сетевых запросов и показано состояние настройки. Сессия привязана к адресу сервиса и аккаунту Яндекс Музыки.

Worker обрабатывает HTTP long polling и ограничивает тело 16 KiB, частоту запросов и число комнат. Ссылки содержат приглашение в URL fragment, не путь/query. Статическая страница работает без трекеров, с no-store/no-referrer и CSP. Автоматический запуск ОС не обещается. Общий HTTP backend не предоставляет Discord IPC: его нельзя получить простым переносом кода на сервер.

Публикации при изменениях выполняются по событиям плеера/снимкам комнаты, резервная проверка — 200 мс, периодический heartbeat — 5 секунд; позиция экстраполируется по временной привязке. На стороне участников остаётся собственное воспроизведение Яндекс Музыки. Сервис опубликован по адресу https://pulseparty.pulseparty.workers.dev; готовая сборка и манифест настроены на него. См. [CLOUDFLARE.md](CLOUDFLARE.md).

## Исторический вариант 0.1.x: изменённый хост (не используется)

Последнее уточнение пользователя отменило необходимость отдельного сервера и отдельной программы. Основная сборка использует native iroh внутри main-процесса PulseSync-mod. Renderer-аддон остаётся изолированным и общается через узкий loopback API. Это явное расширение хоста, а не обход песочницы.

```text
Изолированный аддон ── HTTP + capability ── встроенный модуль PulseSync
                                              │
                           native iroh ────────┼────── другие компьютеры
                                              │
                           Discord IPC ───────┴────── Discord desktop
```

Отдельный процесс и внешний сервер состояния не запускаются. На устройстве создателя `Rooms` хранит авторитетное состояние; это обычный объект в памяти уже работающей Яндекс Музыки. Loopback HTTP нужен из-за существующего SDK и недоступен извне. Библиотека iroh сама создаёт UDP endpoint в процессе хоста и использует n0 discovery/relays по необходимости.

Серверная реализация `Rooms` разделяется с необязательным HTTP-вариантом. Логика прав, revision/epoch/sequence и таймаутов от транспорта не зависит.

- [Официальный пример](https://github.com/PulseSync-LLC/PulseSync-ExampleAddon), commit `0847c6ffc2c5458d8723b8214a5e65802cf1516d`.
- [PulseSync-mod](https://github.com/PulseSync-LLC/PulseSync-mod), commit `ca66618a0084e1d24815bf6ba2ca32560a32af02`.
- [Iroh для JavaScript](https://docs.iroh.computer/languages/javascript), `@number0/iroh@1.2.0` и его реальные TypeScript-декларации.
- [Iroh в браузере](https://docs.iroh.computer/languages/wasm-browser): браузерная реализация требует WASM и relay, UDP hole punching там отсутствует; официального готового browser npm-пакета нет.

SDK:

|---|---|
| Lifecycle | `defineAddon.start`, `api.signal`, `api.onCleanup` |
| UI | слот `playerBarButton`, SDK `Button`, `IconButton`, `Tooltip`, `api.modals.open` |

| Выбор трека | `api.client.playTrackById(trackId,{albumId})` |
| Перемотка | `api.client.setProgress(seconds)` |
| Пауза | `api.client.togglePlayPause()` после чтения фактического состояния |
| Настройки мода | `api.modSettings.get('modSettings.discordRPC.enable')`; обязателен префикс `modSettings.` |
| Discord/native | В текущем AddonApi отсутствуют |

В исходниках `webModules/pulsesyncRuntime/src/features/addonCapabilities.ts` снимок содержит `track.duration` из meta; `progress.position` сохраняется в секундах плеера. `webModules/pulsesyncRuntime/src/api/pulsesyncApi.ts` передаёт аргумент `setProgress` напрямую runtime-плееру. На границе `src/player-adapter.ts` `position` переводится в миллисекунды, `duration` остаётся миллисекундами, seek переводится обратно в секунды. Методы `play()` и `pause()` в исследованном runtime оба являются toggle; адаптер поэтому использует явную проверку и `togglePlayPause`.

`src/main/lib/handlers/handleHeadersReceived/corsHandler.js::matchesAllowedUrl` сопоставляет точный origin и префикс pathname, не wildcard. Основной манифест разрешает только `http://127.0.0.1:18787/v1`.

`src/main/lib/pulsesync/addonNetworkPolicy.js` ограничивает запросы отдельного изолированного origin по манифесту. Официальный `IsolatedModuleRuntime` отклоняет WASM-модули с импортами. Просто установить native npm-пакет iroh в renderer или подменить SDK net на WebSocket нельзя считать поддерживаемой интеграцией. Поэтому native iroh подключается на стороне main через явное изменение исходников хоста.

Настоящий deep link Яндекс Музыки — `yandexmusic://`, а `pulsesync://join` не подтверждён. Встроенная часть явно регистрирует собственный `pulseparty://` и обрабатывает только фиксированный формат приглашения.

## Протокол iroh

ALPN: `pulseparty/1`. Все приглашения имеют вид `pp1.<endpoint public key hex64>.<invite base64url43>`. В коде нет произвольного URL, relay, IP, порта, пути к файлу или команды. Длина 112 символов подходит для передачи в join secret. Используются preset n0, lookup по идентичности и инфраструктура, выбранная библиотекой.

Одно QUIC-соединение несёт отдельные bidi streams запрос/ответ: join, snapshot, action, poll, check. Сообщения имеют лимиты 16 KiB / 64 KiB, схему и таймауты. На удалённого peer ограничены частота запросов и количество одновременных потоков. Повторяемая команда содержит opId. Bearer-сессия отдельна от приглашения.

Координатор — endpoint создателя. Владелец и ведущий хранятся отдельно. Перенос владельца меняет права, перенос пульта — ведущего и epoch. Endpoint координатора не мигрирует: для продолжения требуется открытое приложение создателя. Это явное ограничение P2P-режима.

Клиент принимает только более новую revision этой комнаты. Старый ведущий отклоняется немедленно после смены epoch. Сначала новый ведущий принимает трек и позицию, затем подтверждает `ready`, затем публикует свои действия. После reconnect он получает sequence из snapshot. Если тот же ведущий вернулся после grace без преемника, повторно подтверждает ready. Передачи не создают два источника команд.

Плеер синхронизируется последовательно, каждая операция проверяет generation и AbortSignal. Смена комнаты, epoch или трека отменяет применение старого состояния. До загрузки нужного трека seek не выполняется. Мелкая погрешность не вызывает перемотку. На паузе позиция не растёт; при игре экстраполируется от серверной отметки. Часы калибруются только короткими HTTP/P2P запросами; время ожидания long poll не принимается за RTT. Есть повторная калибровка после изменения системных часов и при конфликте sampledAt.

## Права и приватность

Каждое действие проверяет `Rooms`. Ведущий не получает право закрывать комнату или удалять участников. Самовольная локальная смена трека слушателя корректируется без изменения общей комнаты; громкость не участвует в протоколе. Ошибку недоступного трека хранит только соответствующий участник, следующий трек продолжает обрабатываться.

Приглашения случайные, отзываемые и ограничены TTL. Владелец может удалить участника с одновременным отзывом всех приглашений. Без отзыва общего приглашения удалённый человек смог бы заново войти под новым именем; интерфейс удаления по умолчанию отзывает ссылки. Имена не считаются проверенной Discord-личностью.

Loopback проверяет Host, Origin, JSON и случайный capability. Секрет не вшит в аддон и обновляется при старте main-процесса. Он доступен установленным SDK-аддонам через хост; защита рассчитана на случайные сайты и удалённые запросы, не на уже доверенный вредоносный код внутри хоста. Сетевой интерфейс не принимает произвольные команды ОС.

Журнала приглашений/токенов нет. Учётные данные Яндекса и Discord в протоколе отсутствуют. Соединения iroh шифруются между endpoint-ами; публичные relay видят метаданные, а прямые соединения раскрывают IP peer-ам. [Политика публичных relay](https://docs.iroh.computer/iroh-services/relays/public).

## Discord

Исследованы [Rich Presence](https://docs.discord.com/developers/discord-social-sdk/development-guides/setting-rich-presence), [Invites](https://docs.discord.com/developers/discord-social-sdk/development-guides/managing-game-invites) и [Social SDK 1.11.24259](https://discord.com/developers/docs/social-sdk/release_notes.html). Listening существует. Официальные API включают SetActivityJoinCallback, RegisterLaunchCommand и Desktop platforms. Нельзя переносить гарантии Social SDK на другой RPC-транспорт без проверки.

Основная версия использует встроенную библиотеку `@xhayper/discord-rpc@1.5.1`: локальное IPC, собственный Application ID, `ACTIVITY_JOIN`, явную подписку, party и короткоживущий секрет. Нет запросов друзей, автоматической рассылки, selfbot или пользовательского token. RPC joinability зависит от успешной подписки. Нативный invite и холодный запуск в настоящем клиенте остаются непроверенными; это не скрывается за заполненными полями presence.

Неактивная/закрытая/полная комната не получает join secret. Принятие приглашения проверяется координатором и ожидает решения пользователя. Pending queue ограничена, дедуплицируется, TTL 180 секунд. Показ активности выключен по умолчанию. Обычный RPC PulseSync нужно выключить вручную: `src/main/lib/discordRichPresence.js` не содержит официального механизма передачи владения presence аддону. Обратное восстановление чужих настроек не обещается и не выполняется.
