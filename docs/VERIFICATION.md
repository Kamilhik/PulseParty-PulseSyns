# Отчёт о проверках

## Обновление 0.3.0 — 19.11.2026

- Автоматическое имя: видимый ник из нативного UserProfile, fallback — `api.user.getLogin()`. Поле не редактируется вручную. При восстановлении сессии старое имя обновляется отдельным действием.
- Все всплывающие уведомления коррекции удалены, включая смену трека, seek и паузу. Проверка отслеживает пустой toast-стенд при нескольких переключениях.
- Синхронизация просыпается по `player.onChange` и принятым снимкам, операции остаются последовательными. Резервная проверка 200 мс; загрузка трека проверяется сразу, затем каждые 50 мс. Периодические публикации остаются раз в 5 секунд, изменения отправляются сразу после обработки события.
- Настройка `skipMode`: owner/everyone, только владелец может менять. Сервер ставит ограниченную очередь команд, исполнение доступно текущему ведущему. ID команд, epoch, TTL и подтверждение защищают от повтора и исполнения после handoff. Политика относится к кнопкам комнаты; переданный ведущему пульт сохраняет его управление обычным плеером.
- 28 автотестов пройдены, включая запрет обхода политики, истечение/смену epoch и потерю ACK без двойного native skip.
- Локальный workerd и браузерный сценарий: три клиента, имена из SDK, оба режима доступа, переключения вперёд/назад через удалённого ведущего, пауза, handoff и закрытие. На localhost последнее измерение распространения переключения — 121 мс (предыдущая версия — 881 мс). Это единичные измерения метаданных, не статистика и не аудиорасхождение.
- Cloudflare Worker обновлён до версии `f19a0feb-b5a9-430e-80bf-25dadf2c4c4e`, адрес прежний. Для нового набора команд используется новый ключ координатора `pulseparty-rooms-v2`: ранее уже живший объект продолжал принимать старую схему после первой публикации. Публичный `/v1/health` теперь содержит build `0.3.0`, и проверка требует его перед функциональными запросами.
- Публичный HTTPS-сценарий трёх HTTP-клиентов пройден с новой политикой, очередью команд и rename. Полный браузерный сценарий поверх опубликованного HTTPS также пройден; измерение того же переключения — 122 мс с тестовыми адаптерами плеера.
- Аддон установлен и перезагружен в настоящем PulseSync. Непосредственно в клиенте проверено имя `Kamilchik` из видимого профиля, создание комнаты, текущий реально играющий трек с обложкой, роль владельца/ведущего и новая настройка «Кто может переключать треки». Новая комната оставлена открытой. Разницу слышимого воспроизведения между двумя компьютерами эти проверки не измеряют.

Дата: 18.11.2026, Europe/Moscow. Состояние реализации — первый рабочий интеграционный прототип; полностью завершённым сценарием первоначального ТЗ он не объявляется.

В браузерном сценарии прошли: создание комнаты, копирование приглашения, вход двух друзей, трек 123, передача пульта Борису, выбор трека 456, передача Вере, пауза, закрытие комнаты и завершение сессий остальных участников. Измеренная задержка распространения одного переключения после пользовательского действия — **379 мс** в последнем запуске на localhost, 391 мс в предыдущем. Старый HTTP-стенд показал 386 мс. Это не оценка реального аудиорасхождения между компьютерами и не статистический SLA.

Тесты синхронизации проверяют перевод секунд/миллисекунд, загрузку перед seek, порог и cooldown, сохранение громкости, недоступную песню с переходом к следующей, принятие состояния новым ведущим, отмену устаревшего epoch, stop и восстановление hostReady. Проверяются отклонение чужих/старых команд, дубликаты opId и sequence, истечение/отзыв приглашений, kick, лимит комнаты и grace failover. Loopback-тесты проверяют Host, Origin, pairing в legacy-режиме, capability во встроенном режиме и конфликт presence.

## Не выполнено / нельзя считать доказанным

- Реальная установка изменённого PulseSync-mod и загрузка аддона в Яндекс Музыке. Установленный `app.asar` не перепаковывался и приложение для проверки не запускалось.
- Воспроизведение и слышимое расхождение между двумя настоящими аккаунтами/компьютерами.
- Соединение iroh между разными NAT и принудительный relay-only fallback. Отдельная проверка default n0 preset подтвердила online и вход по endpoint lookup на одной машине, но не доказывает маршрут между разными NAT. Автоматические UI/room тесты используют тестовый resolver с loopback-адресами.
- Настоящий Discord Rich Presence с собственным Application ID, вид со второго аккаунта, UI отправки invite, RPC-подписка в реальном клиенте, callback принятия и холодный запуск. Application ID не предоставлен, фиктивный не создавался.
- Компиляция официального Social SDK companion: его архив, CMake и C++ toolchain отсутствуют. Он не нужен основной встроенной сборке.
- Docker/Compose: CLI Docker здесь отсутствует; файлы подготовлены, контейнерная сборка не запускалась.
- macOS/Linux бинарники, URL scheme registration и запуск под ними.

Применён `frontend-design`. Аудитория — небольшая компания друзей; основное действие — создать/открыть комнату и передать пульт. Ограничения — русскоязычная компактная панель внутри существующего плеера, dark mode, системная типографика, отсутствие дополнительных шрифтов и внешней аналитики.

Рассматривались «микшерная панель», «музыкальный журнал» и «комната плеера»; выбран последний вариант, согласованный с Яндекс Музыкой.
